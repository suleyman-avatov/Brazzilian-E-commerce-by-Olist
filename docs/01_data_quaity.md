# Качество данных

Результаты проверок сырых таблиц Olist (слой `raw` в DuckDB). Запросы лежат в `sql/01_raw/02_checks.sql` и `sql/02_staging/01_quality_checks.sql`.

## Итог

Данные хорошего качества: ключи уникальны, связей без пары нет, критичных ошибок не обнаружено. Найденные проблемы небольшие и закрываются простыми правилами очистки (см. ниже). Главное ограничение для анализа не в качестве, а в структуре данных: повторных покупателей мало.

## Целостность и связи

- Дублей ключей нет в `orders`, `customers`, `products`, `sellers`, `order_items` (`order_id`, `order_item_id`) и `order_payments` (`order_id`, `payment_sequential`).
- В `order_reviews` значение `review_id` повторяется 814 раз: один и тот же `review_id` встречается у разных заказов. Поэтому грейн отзыва это заказ, а не `review_id`.
- Осиротевших записей нет ни в одной связи (заказы → клиенты, позиции → заказы, продукты, продавцы, платежи → заказы, отзывы → заказы).
- 775 заказов без позиций, все недоставленные: `unavailable` 603, `canceled` 164, `created` 5, `invoiced` 2, `shipped` 1.

## Клиенты

- `customer_id` уникален для каждого заказа (99 441), а реальных клиентов по `customer_unique_id` 96 096.
- Разница в 3 345 означает, что повторных заказов не больше 3 345, то есть клиентов с 2 и более заказами **не больше 3,5%**.

## Даты

- Заказов с датой доставки, но не в статусе `delivered`: 6.

- Обещанная дата доставки хранится без времени (у всех 99 441 заказов 00:00:00), поэтому задержка считается по календарным дням.

## Задержки и сроки доставки

- Рабочая выборка: 96 470 доставленных заказов с датой доставки.
- Опоздавших по календарным дням: 6 534 заказа, то есть около **6,8%**.
- Срок доставки: минимум 0 дней, медиана 10, 99-й процентиль 46, максимум 210. Хвост длинный, но это реальные данные, поэтому выбросы не удаляются.

## Отзывы

- Оценки: 1 звезда 11 424, 2 звезды 3 151, 3 звезды 8 179, 4 звезды 19 142, 5 звёзд 57 328. Плохих (1-2) около 14,7%, нейтральных около 8,2%, хороших (4-5) около 77,1%.
- У 98 126 заказов один отзыв, у 547 два или три, поэтому **768 заказов вообще без отзыва**.
- Совпадений по времени ответа у нескольких отзывов одного заказа нет, значит, выбор «последнего отзыва» однозначен.

## Геолокация

- 1 000 163 строки приходятся на 19 015 уникальных почтовых префиксов, то есть на префикс в среднем много точек. Прямое соединение с заказами размножило бы строки.
- Без координат 278 клиентов и 7 продавцов.

## Цены и доставка

- Цена: минимум 0,85, медиана 74,99, 99-й процентиль 890, максимум 6 735. Нулевых и отрицательных цен нет.
- Стоимость доставки: минимум 0, 99-й процентиль 84,52, максимум 409,68.
- Распределения с длинным правым хвостом, поэтому используем медианы и доверительные интервалы.

## Решения для слоя staging

1. Базовая выборка: `order_status = 'delivered'` и непустая дата доставки.
2. `is_late` и `delay_days` по календарным дням.
3. `delivery_days`: число дней от покупки до доставки.
4. Флаг `date_anomaly` для 23 заказов с доставкой раньше передачи перевозчику.
5. Один отзыв на заказ (последний по `review_answer_timestamp`), заказы без отзыва остаются с пустой оценкой.
6. `order_value`: сумма `price + freight_value` по позициям, агрегируется до соединения с другими таблицами.
7. Категория на английском: `unknown` для пропусков, перевод двух категорий добавляется вручную.
8. Геолокация сводится к одной строке на почтовый префикс (медиана координат), расстояние для клиентов и продавцов без координат остаётся пустым.
9. Выбросы по цене и срокам доставки не удаляются.

## Что это значит для анализа

- Для H3 в группе с задержкой повторных покупателей будет немного (по порядку величины десятки), поэтому нужны доверительные интервалы, а мощность проверяется заранее.
- Пик ноября 2017 может быть искажающим фактором (сезонность), его нужно учесть при проверке H1 и H3.
- Платежи и позиции имеют по нескольку строк на заказ, поэтому все суммы считаются агрегатом до соединения.
